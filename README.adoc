= ITU publications bibliographic data for Relaton-ITU

This repository holds the *combined* bibliographic data for both ITU sectors —
ITU-R (Radiocommunication) and ITU-T (Telecommunication Standardization) — used
by Relaton-ITU. It supersedes the ITU-R-only
https://github.com/relaton/relaton-data-itu-r[relaton-data-itu-r] repository.

Data is stored in Relaton YAML format in a single flat `data/` folder, with the
two sectors distinguished by filename prefix (`data/itu-r-*` and
`data/report-itu-r-*` vs `data/itu-t-*`). A single top-level `data/` is what
`relaton index --flavor itu` scans, matching every other `relaton-data-*`
repository:

* `data/itu-r-*`, `data/report-itu-r-*` — ITU-R Recommendations, Reports,
  Questions, Resolutions and Handbooks. ITU decommissioned the `RunSearch`
  bulk-enumeration endpoint this corpus was originally migrated with, so it is
  *crawled from the `/pub` + `/rec` pages ITU still renders* (relaton#112).
  Reports carry their own identity — a docid leading with `Report ` (relaton#110)
  — which is why the sector needs two filename prefixes.
* `data/itu-t-*` — ITU-T Recommendations (and supplements/amendments/corrigenda).
  Harvested from the ITU-T recommendation index
  (`mws/api/recommendations/searchRecs`, issue relaton-itu#80).

== Crawler

`crawler.rb` runs via `.github/workflows/crawler.yml`: a full crawl on Sundays at
14:00 UTC, a top-up Monday to Saturday, and on manual dispatch, which takes the
mode as a `full`/`top_up` choice. The mode reaches the script as `ARGV[0]`, which
it turns into `RELATON_ITU_MODE` before anything reads it. Each run:

1. wipes the index, and — on a full run — the `data/` files of both sectors;
2. on a top-up, re-derives the index rows of every record it is about to skip
   (`#index_files`, once per sector), since a skipped record is never parsed and
   so never indexed;
3. crawls ITU-R from `/pub` + `/rec`
   (`Relaton::Itu::DataFetcher#fetch_publications`);
4. harvests ITU-T from `searchRecs`, merging its rows into the same index
   (`Relaton::Itu::DataFetcher#fetch_recommendations`);
5. writes the combined `index-v2.yaml` and rebuilds `index-v2.zip`.

Steps 3 and 4 share one fetcher, so both sectors go through the same identifier
guard and the same unparseable-id report — ids that cannot be indexed are named
in the log, and raised as an "Error fetching documents" GitHub issue when
`GITHUB_REPOSITORY` and `GITHUB_TOKEN` are set.

`RELATON_ITU_MODE` — set from the command line, `ruby crawler.rb full|top_up` —
selects how much of the corpus a run re-derives. Both sectors honour it:

* `full` (the default) wipes the data files and re-fetches every edition of every
  document, which makes ITU the sole author of the corpus. ~3.5 h — ITU-R ~2 h,
  ITU-T ~1.6 h — which is why one job can still do both. It is also the only run
  that *prunes*: a top-up never deletes, so a withdrawn edition would otherwise
  linger forever.
* `top_up` walks the same documents but fetches only what the dataset does not
  already hold: ITU-R per edition, ITU-T per recommendation family, since a new
  edition changes its siblings' `hasEdition` relations. Both decide from the
  enumeration row alone, with no extra requests, so it does not wipe. ~0.6 h on a
  quiet day, nearly all of it ITU-R enumeration.

The first run against a dataset that predates relaton#110 must be `full`: a
`top_up` would add every Report a second time under its new `Report …` name,
beside the old-named copy. The crawler refuses such a run before it starts
(`.guard_report_seed`), and only a full run retires the old names.

`RELATON_ITU_DELAY` (default `1.0`) is the politeness pause. It is the minimum gap
between request _starts_, shared by the ITU-R worker pool
(`RELATON_ITU_R_CONCURRENCY`, default 4), rather than slept before each request, so
`www.itu.int` sees at most 1 request/s however many workers run. Lower it at your
peril — at 0.4 s a corpus run lost whole series to ITU's WAF.
`RELATON_ITU_R_CONCURRENCY=1 RELATON_ITU_PACE=fixed` restores the pre-pool request
profile exactly.

Each ITU-T record is enriched (abstract, ISO/IEC co-identifier, status, edition,
publisher + editorial-group contributors, relations) so a harvested record
matches what a live lookup returns. That costs ~4 `www.itu.int` requests per
record over ~16k records, so the fetcher spreads them over a worker pool —
`RELATON_ITU_CONCURRENCY` (default 8) tunes it; lower it if ITU starts
throttling. The pool also shares a per-recommendation detail cache
(`RELATON_ITU_CACHE_ENTRIES`, default 512; `0` disables it), since two of the four
requests answer per recommendation rather than per edition.

Four guards refuse to publish a bad crawl: one refuses a top-up onto a
pre-relaton#110 dataset, before it spends the hours; one blocks a collapse in the
ITU-T file count; one blocks a collapse in the ITU-R file count *per family*
(Recommendations, Reports, Questions/Handbooks, Resolutions), because ITU
throttles `/rec` and `/pub` differently and a healthy Recommendation crawl would
otherwise mask a Reports crawl that lost every series; and one blocks a corpus
where enrichment largely failed (fewer than 90% of records carrying
`contributor:`), which is what a mid-crawl block by ITU's WAF looks like.

The last three count files, and a top-up never deletes any, so only the seed guard
can fire on a Monday-to-Saturday run. The weekly full run, where the wipe makes
them load-bearing, is the real check. What protects a top-up instead is step 2
above: the index rows come from disk, so a degraded harvest costs new records
rather than published ones.

== Index

Both sectors serialize to the same `pubid:itu` structured `index-v2`, so one
index holds ITU-R and ITU-T rows together:

* `index-v2.yaml`/`.zip` — pubid-structured index (rows carry
  `_type: pubid:itu:*`), consumed by the `Relaton::Itu` flavor.

Each row's id is kept only if it round-trips
(`from_hash(to_hash).to_hash == to_hash`) through `::Pubid::Itu`, the same guard
`Relaton::Itu::DataFetcher#pubid` and the index loader's
`Relaton::Index::FileIO#id_supported?` apply, so producer and consumer stay
aligned. A handful of malformed/series-level ids that pubid does not model are
written as data files but left unindexed.

Verify the published index with:

[source,sh]
----
bundle exec rspec
----

NOTE: `index-v2` must be produced by the same relaton/pubid the flavor consumes —
see the pins and comments in `Gemfile`.
